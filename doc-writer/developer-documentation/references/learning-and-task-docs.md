# Learning and task documentation

## README contract

Pass the first-screen test:

1. project name and one-sentence value;
2. who it is for / primary use case;
3. shortest verified quickstart;
4. expected result;
5. links to deeper docs, support, contribution, and license.

Then cover prerequisites, installation, core usage, configuration, architecture only if needed for adoption, troubleshooting, compatibility/security, and project status. Avoid a long table of contents before the reader understands the project.

## Tutorial

A tutorial teaches through a controlled success path. Define what the learner builds and learns, list exact prerequisites, start from a clean state, use small verified steps, show checkpoints/expected results, explain only concepts needed now, include cleanup, and point to how-to/reference next.

Do not branch into many options. Choose one reliable path and disclose that alternatives exist.

## How-to guide

A how-to assumes basic competence and solves one real task. Use a task-based title, state starting conditions, provide ordered actions, include decision branches only when needed, verify the outcome, cover common failure/rollback, and link reference rather than restating it.

## Explanation

Explain why, trade-offs, boundaries, mental model, and relationship to alternatives. Avoid turning explanation into setup instructions. Connect concepts to concrete components and decisions in the project.
