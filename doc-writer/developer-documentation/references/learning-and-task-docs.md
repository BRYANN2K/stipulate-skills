# Learning and task documentation

These are page-design heuristics, not mandatory templates or a reason to reorganize an established docs set.

## README

Help the intended reader quickly determine what the project is, whether it fits, and the shortest supported path to a meaningful result. Add prerequisites, expected result, deeper links, support, contribution, license, architecture, compatibility, security, or status only as the project and audience need them. A focused library README and a platform repository README will differ.

## Guided learning

Choose one dependable path that teaches the requested concept through doing. State the starting conditions, show meaningful checkpoints, explain concepts near the step that needs them, and include cleanup or next paths when relevant. Avoid presenting every alternative before the learner reaches a first result.

## Task guide

Solve one real task for a reader with the assumed background. State starting conditions, provide the shortest safe actions, branch only where the decision matters, and show how to recognize success or recover from common failure. Link to canonical reference instead of duplicating it.

## Conceptual explanation

Clarify the mental model, boundaries, rationale, relationships, and trade-offs needed to understand the subject. Connect the explanation to concrete project components or decisions without turning it into a setup script.
