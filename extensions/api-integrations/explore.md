# api-integrations — explorer

Définir et vérifier une frontière API, ses identités, erreurs, répétitions et versions.

## Décider de la pertinence

La disponibilité dans la configuration n’active pas ce métier. Pendant `spec-explore`, sélectionner cette extension seulement si sa responsabilité touche le changement ou une inconnue décisive. Ne pas lancer tout le catalogue. Exemple pertinent : Intégrer un webhook avec signature, doublons, délai et réponse partielle. Exemple hors périmètre : Modifier une fonction purement locale sans frontière API.

Cette extension sécurise les frontières entre un produit et une API : découverte du contrat, authentification, encodage, erreurs, délais, retries, idempotence, pagination, versionnement et compatibilité. Elle s’active dans `spec-explore` lorsqu’un changement consomme, expose ou remplace une API HTTP, OAuth, webhook ou service externe, ou lorsqu’un SDK masque une décision de contrat. Elle s’active aussi pour une modification interne si des clients ou intégrations existants peuvent observer le changement.

Elle ne s’active pas pour une fonction purement locale sans frontière réseau. Elle ne remplace pas la conception métier, la sécurité globale, l’extension `backend-engineering` ni le fournisseur distant. OpenAPI définit un langage indépendant pour décrire les interfaces HTTP afin que les humains et les outils puissent découvrir les capacités sans lire le code ([OpenAPI Specification](https://spec.openapis.org/oas/latest.html)). RFC 9110 définit la sémantique HTTP : méthodes, statuts, en-têtes, contenu et contraintes de la communication requête/réponse ([HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)). Ce sont des contrats de protocole, pas une preuve que le fournisseur est fiable ou que chaque champ est adapté au produit.

## Reconnaître et réutiliser l’existant

Pour un projet neuf, chercher la spécification ou documentation versionnée, les environnements, les credentials et scopes, les limites de débit, les exemples de requêtes/réponses, les délais, les webhooks, le propriétaire et la politique de changement du fournisseur. Pour un projet en cours, capturer une requête réelle dans un environnement sûr, comparer le schéma consommé au schéma publié, lire les tests de contrat, inspecter la gestion des secrets, des statuts et des retries, puis vérifier si l’intégration est réellement utilisée. Classer chaque constat comme **établi** (contrat, test ou réponse reproductible), **inféré** (documentation non vérifiée), **incomplet** (une direction ou une version manque), **manquant** (recherche sans artefact) ou **non applicable** (aucune frontière concernée). Un SDK installé ne prouve pas la version réellement appelée ; un 200 ne prouve ni la forme des erreurs ni la compatibilité future.

OAuth 2.0 sépare notamment client, propriétaire de ressource, serveur d’autorisation et serveur de ressources, et fait circuler un access token vers la ressource ([RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749.html)). Pour les choix de sécurité actuels, la Best Current Practice OAuth 2.0 de l’IETF met à jour le modèle de menace, recommande des protections comme PKCE selon le flux et déprécie certains modes moins sûrs ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)). RFC 6749 décrit donc le modèle de protocole ; RFC 9700 porte les recommandations de sécurité et peut faire apparaître un enjeu de compatibilité à traiter explicitement. Stripe documente les clés d’idempotence pour rejouer une requête sans créer deux effets, avec conservation du premier résultat pendant la fenêtre documentée ([Idempotent requests](https://docs.stripe.com/api/idempotent_requests?lang=curl)). Ces références encadrent des choix précis ; elles ne justifient pas de réessayer toute mutation ni de stocker un token sans politique de rotation.

Consulter la carte du bootstrap puis rechercher seulement les preuves utiles au changement. Pour chaque élément, noter **établi, inféré, incomplet, manquant ou non applicable**, avec preuve ou justification. Ne pas confondre absence de document et absence de pratique. Décider de réutiliser, compléter ou remplacer ; une étape déjà satisfaite peut ne demander aucun travail.

## Borner la contribution au contrat commun

Le MVP comprend le contrat versionné des opérations utilisées, un flux d’authentification minimal, secrets hors dépôt, timeout, gestion d’une erreur, un test de contrat et une procédure de désactivation. Approfondir si l’API écrit de l’argent ou des données, reçoit des webhooks, traite des informations sensibles, a plusieurs clients, des quotas serrés ou une compatibilité incertaine : vérifier rotation, moindre privilège, signature/rejeu des webhooks, idempotence de chaque mutation, compatibilité ascendante, observabilité par fournisseur et plan de dégradation. La présence d’un SDK n’est pas une stratégie d’intégration.

Proposer seulement les propriétés nécessaires et leurs moyens de vérification, en utilisant les candidats de [check.md](check.md). L’agent les adapte et les remappe en identifiants `AC-1`, `AC-2`, etc., uniques dans la **spec commune** ; le moteur ne remappe aucun identifiant métier. Ne pas créer une approbation ou une spec parallèle. Chaque critère doit préciser résultat, contexte et preuve attendue. Une nouvelle exigence après accord impose révision et nouvel accord sur le contrat.

## Frontières

`backend-engineering` porte le chemin métier, la concurrence et le rollback ; `database-engineering` vérifie persistance et transactions ; `frontend-engineering` traduit les erreurs en états compréhensibles ; `ai-engineering` peut fournir un outil mais ne supprime pas les contrôles d’autorisation. Éviter de réessayer aveuglément les POST, de journaliser les tokens, de traiter un 200 comme une réussite métier, de confondre compatibilité de schéma et compatibilité sémantique, ou de dépendre d’un sandbox plus permissif que la production. Une URL interne jamais appelée ne déclenche pas l’extension ; une API qui change le contenu visible peut la déclencher même sans changement de code client.

Les autres métiers cités sont des collaborations possibles, jamais des dépendances automatiquement activées. Le travail cloud seul n’active pas UX/design. Les sources détaillées sont dans [sources.md](sources.md) ; elles éclairent les décisions et ne constituent pas des critères supplémentaires implicites.
