# Application and dashboard profile

Load this profile for authenticated applications, admin tools, operational interfaces, and analytical dashboards. Their primary job is operation or decision support, not a landing-page funnel. A targeted system, motion, copy, or QA task uses only the relevant branch.

## Route by scope

### Bounded work in an established system

Inspect the canonical tokens, primitives, navigation, density, data contracts, permissions, and affected states. Inherit and extend them directly. Make one recommendation and implement the bounded request; do not create marketing copy, alternative concepts, or a new system document merely to satisfy a process.

### New flow, major pattern, or open information architecture

Capture a compact task brief only if it supplies missing decisions. When constraints already select the pattern, one viewable recommendation is valid. When a real topology or interaction trade-off remains, render enough concepts of the same useful slice to resolve it. Compare structure, navigation, hierarchy, density, disclosure, action placement, responsive behavior, and state handling—not palette skins.

## Task truth

Keep the relevant subset of:

- actor, job, route, entry condition, and success condition;
- source/grain/freshness of displayed data and synthetic-fixture labels;
- permissions and visibility rules;
- mutations, confirmation/undo, pending/retry/reconciliation behavior;
- states material to the requested task;
- behavior-changing viewport constraints and inherited visual world;
- decision owner when a real choice exists.

Use application/dashboard engineering as the authority for routes, auth, state, data, metrics, and mutations. Design notes do not replace those contracts. Inline notes are valid; persist only when the user/project or cross-run handoff needs them.

## Storyboard only when flow is open

Show enough frames to expose the primary task and any consequential transition or recovery. Each frame may record:

```text
route/state → user question/action → visible data/content → permission/mutation
→ feedback/recovery → next frame
```

Do not fill a dashboard with invented numbers for visual density. A bounded label, component, or state change can skip a new storyboard when the governing flow is already clear.

## Concepts when needed

Use the same representative task/data/state for fair comparison. Every candidate should make a coherent decision about the applicable topology, navigation/focus model, hierarchy/density, disclosure, action placement, responsive behavior, and state handling. Include a product-specific signature, trade-off, and no-go only when they help select or implement the direction.

Stop adding candidates when the real trade-off is covered. If variants are interchangeable or only colors change, collapse to one recommendation.

## Build and review

Build the smallest vertical slice that completes or falsifies the requested pattern. Preserve the existing system and update shared rules only when the request includes system work or real reuse appears.

Choose captured viewports and states from changed behavior and claim. A dense default, non-happy state, or narrow alternative is necessary only when applicable to the requested task or completion statement. Review the relevant subset of:

- task completion and state visibility;
- source, grain, freshness, metric, permission, and action truth;
- dense hierarchy, table/chart behavior, overflow, and any behavior-changing narrow alternative;
- keyboard/focus, semantic controls, pending/retry/undo/reconciliation;
- console/network and applicable accessibility probes;
- synthetic data labels and absence of fake business/customer proof.

A targeted check reports its exclusions and does not imply full application quality. Local UI authority never authorizes real resource mutation, production credentials/data, dependency changes, deployment, or publication.
