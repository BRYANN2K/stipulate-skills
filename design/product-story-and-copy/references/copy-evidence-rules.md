# Copy and evidence rules

## Claim classes

| Class | Minimum evidence | Publishability |
|---|---|---|
| Capability | Current code, product docs, or verified demo proving the exact scope | Publish only at supported scope |
| Performance | Reproducible benchmark with environment, sample, baseline, and date | Publish with method and bounds |
| Customer outcome | Attributable case study or approved customer evidence | Never turn an anecdote into a general guarantee |
| Testimonial | Approved exact quote, identity/display consent, and source | Never synthesize or paraphrase as a quotation |
| Comparison | Current evidence for both products and a defined dimension | Date and scope; avoid universal “best” claims |
| Security/compliance | Authoritative control, audit, certification, or policy evidence | Name the control and boundary; never infer certification |
| Availability | Current regions, plans, limits, and operational constraints | Distinguish released, beta, planned, and unavailable |
| Popularity | Current attributable count and definition | Avoid vanity numbers without relevance |

## Evidence precedence

Prefer, in order:

1. current product behavior and authoritative source code/configuration;
2. current first-party product or policy documentation;
3. approved research, analytics, and customer evidence;
4. named inference from verified facts;
5. hypothesis clearly excluded from publishable copy.

Search snippets, generated summaries, competitor copy, and visual mockups are discovery evidence only.

## Anti-slop signals

Flag rather than blindly ban:

- unsupported superlatives or universal claims;
- abstract transformation without a mechanism;
- three-adjective stacks;
- identical sentence rhythm across every section;
- fake intimacy, rhetorical questions, or manufactured founder vulnerability;
- “from X to Y” contrasts that erase real constraints;
- generic CTA labels detached from the resulting action;
- numbers selected because they look persuasive;
- feature lists relabeled as benefits without user context;
- invented testimonials, logos, trust badges, or “live” activity.

A common word is acceptable when it is the clearest exact word. The audit evaluates meaning, not a blacklist.

## Interface state copy

| State | Must answer |
|---|---|
| Loading | What is happening, and should the user wait or continue? |
| Empty | Is this first use, no match, no permission, or genuinely no data? |
| Validation error | Which field failed and how can it be corrected? |
| Server error | What failed, what remained safe, and what can be retried? |
| Success | What changed, where is it visible, and what is the next useful action? |
| Destructive confirmation | Which exact resource and irreversible effect are involved? |
| Permission | What is unavailable and who or what can change access? |

## Marketing-readiness boundary

Copy can specify title, description, heading, social, canonical, conversion, trust, and schema requirements. It cannot prove implementation, indexability, analytics delivery, consent behavior, page performance, or browser accessibility. Route those claims to implementation and runtime verification.
